# File sharing

Chat messages carry file metadata and the sender's node ID. Large files are copied into the sender's local Iroh blob store when offered. Their bytes are never written into the replicated message document or pushed to other members. A recipient chooses a destination and clicks **Download**; the blob downloader then requests the hash from the offering peer. The saved file is written through a temporary file, and a replicated receipt is recorded only after the save completes.

Files up to 8 MiB that decode as images, and UTF-8 text files up to 64 KiB, are inline attachments. These use the existing automatic peer transfer path and record a receipt once the blob arrives. A received image above the local maximum image size can still be downloaded explicitly. The local **Keep history** setting controls whether inline content is downloaded and how long its blob tag is retained. Expired inline content is skipped during initial sync, retries, and direct pushes. Attachment and receive records remain visible regardless of that local history window; an explicit delete or history clear still removes the corresponding chat record. The offering peer must be online to serve a new download request.

Inline text is stored on each receiving device, including the sender's device, while its local history policy retains it. **Unlimited** keeps it until history is cleared. **Save** writes an additional copy wherever the user chooses; changing chat retention cannot delete that saved copy.

The sender can select **Stop sharing** on a file offer. This immediately blocks new blob requests and interrupts active reads from this device; the owner-authored sharing state syncs to other members so their cards show the file as unavailable. **Resume sharing** allows requests again. This applies to every offer of identical file contents from this device because the P2P protocol addresses blobs by content hash. The offer and earlier receive receipts remain in chat history, and stopping sharing cannot remove a copy someone has already downloaded. Sender cards show upload progress while a peer downloads, then show sent or interrupted status. "Sent" means Wire finished sending the bytes; a **Received by** entry appears only after the recipient saves the file and its receipt syncs.

For explicit downloads, Wire saves the chosen destination and pins any partial blob locally. Iroh retries short connection failures and requests missing verified chunks. The file card shows received bytes and switches to **Connection stalled · retrying** after ten seconds without progress; known offline owners are identified in the card. When retries or the transfer timeout end, the card shows **Paused** and **Resume**. Restarting Wire restores the paused request and destination, so Resume can continue from retained chunks. **Cancel** or **Discard** removes the saved request and releases its partial blob pin. A completed download replaces an existing destination through a temporary file, then records the replicated receive receipt. The chat header shows known online or offline presence for direct peers; presence checks run separately from the transfer, so an outage may appear there later than in the file card.

## Manual checkpoint

1. With two peers online, offer a ZIP. Confirm the recipient sees its name, size, and owner without a file appearing on disk or a large background transfer.
2. Click **Download**, choose a destination, and verify the saved bytes match. Confirm the chat shows the recipient under **Received by** after both peers sync, including after restarting Wire.
3. Try a small image and UTF-8 text file. Confirm they appear automatically, the text preview works, and Save writes the original bytes.
4. Offer the same ZIP twice and download one offer. Confirm progress and status stay with the correct message. Take the owner offline mid transfer: expect retrying, then Paused; bring them back and click Resume. Confirm the saved bytes match and no receive receipt appears before completion.
5. Close the recipient during a large download, restart Wire, and confirm the card shows Paused with the original destination. Resume and verify the file. Repeat with Cancel or Discard and confirm the saved request disappears.
6. Choose an existing destination file and confirm a completed transfer replaces its contents. Check that a failed or cancelled transfer leaves the original destination intact.
7. Set a short history policy and revisit an expired inline attachment. Confirm it does not download again while older file offer and receive records remain visible through **Load older messages**.
8. During a large download, check the sender's file card for upload progress. Click **Stop sharing** while bytes are moving: the recipient should pause, a fresh request should fail, and the offer and prior receipts should remain. Click **Resume sharing** and resume the recipient download. Restart the sender while stopped and confirm it stays stopped.
